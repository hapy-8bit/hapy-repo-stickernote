# 原子提交机制与文件损坏防护

关联：[[00_每日贴纸_全景图谱|全景图谱]] · [[Documentation/DATA|数据合同]] · [[AGENTS|工程规范]]

## 1. 媒体与索引提交顺序
系统严格贯彻“**物理文件先落盘，元数据后提交，UI 最后更新**”的铁律：
1. **草稿生成**：新成品 PNG / 蒙版通过 `.partial-<UUID>` 临时文件写入，执行 `fsync` 刷盘后原子 `rename`。
2. **仓库提交**：图像完整就绪后，调用 `LocalStickerRepository` 提交新资产/版本。
3. **所有权转移**：元数据事务提交成功后，`StickerMediaSession.markCommitted()` 将草稿文件转移至长期资产库，清理未使用的多余预览草稿。
4. **失败处理**：中途取消或崩溃，仅清理本次拥有的草稿文件，历史已有文件不受任何触碰。

## 2. 索引原子提交与损坏保护
- **原子替换**：索引存储于 `filesDir/sticker-store.json`（schema 2）。写入时先写 `.pending-<UUID>` 临时文件，刷盘完毕后原子 rename 覆盖旧索引，杜绝半写入坏文件。
- **内存校验与防御性加载**：每次读取重读并严格验证 JSON 结构、ID 唯一性、引用外键完整性、坐标有效性及物理文件存在性。
- **坏索引不静默重置**：如果索引文件损坏，抛出明确异常并完整保留现场文件，绝对禁止静默新建空索引覆盖用户历史数据。
- **向下兼容迁移**：支持平滑读验 schema 1 `journal.json` 并生成对应的 legacy 资产，迁移过程中旧文件始终保留作为恢复线索。
